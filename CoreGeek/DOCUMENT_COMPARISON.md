# 两份开发文档对比分析

## 文档 A：原始代码描述文档（用户首次提供）

> 定位：**代码说明文档** — 描述现有代码"是什么"

### 优势

| # | 优势 | 说明 |
|---|------|------|
| 1 | **简洁精确** | 每个文件用一两句话说清职责，5分钟就能理解整体架构 |
| 2 | **与实际代码一致** | 描述的就是代码当前实现的内容，没有虚构功能 |
| 3 | **数据结构清晰** | request/response 的字段一一列举，带示例值（如 roundNo: 85） |
| 4 | **决策速查表** | "决策目标 → 关键输入字段"的对照表非常实用，开发时快速查阅 |
| 5 | **易错点提醒** | 单独列出"不可选/受限项"，标注只有 build 和 attack 受时间限制 |

### 劣势

| # | 劣势 | 说明 |
|---|------|------|
| 1 | **缺少开拓者细节** | 只说"做任务"，没说明 acceptTask/submitAnswer/summonTreasure 的具体逻辑 |
| 2 | **缺少物品使用** | 没有 use 升级券/药品/炸弹的决策逻辑 |
| 3 | **缺少优先级说明** | 每个角色"先做什么后做什么"的优先级只在表格里，没有代码级描述 |
| 4 | **没有 treasure 相关** | 宝藏召唤只在"决策信息速查表"中提了一句，无实现指引 |
| 5 | **没有夜晚角色分配策略** | 只说"把单位派回炮塔旁"，没说工人和开拓者如何分配 |

---

## 文档 B：详细决策规范文档（用户第二次提供）

> 定位：**决策设计文档** — 描述系统"应该做什么"

### 优势

| # | 优势 | 说明 |
|---|------|------|
| 1 | **决策点全覆盖** | 每个角色的每个决策点都列出了可选动作范围和决策依据 |
| 2 | **表格化优先级** | 工人1/工人2/开拓者各有明确的优先级表格，一目了然 |
| 3 | **攻击策略详细** | 三种武器的目标选择算法都有具体描述（锥形/穿透/溅射） |
| 4 | **全局决策补充** | 金币分配、物品使用、LLM调用等通用决策单独成章 |
| 5 | **补充信息丰富** | 赚钱途径、花钱途径、机器人骚扰、防御圈布置等战术建议 |

### 劣势

| # | 劣势 | 说明 |
|---|------|------|
| 1 | **重复内容多** | 同一个文档被粘贴了4次，冗余严重 |
| 2 | **过于理想化** | 描述的是"应该做"而非"已实现"，容易让开发者误以为功能已完成 |
| 3 | **缺少代码映射** | 没有说明每个决策对应哪个函数/文件，落地困难 |
| 4 | **宝藏召唤只有描述** | "携带任务用品→走到祭坛→summonTreasure"，但祭坛在哪？怎么解析传闻？没有 |
| 5 | **缺少异常处理策略** | `lastRoundRoleActionResults` 的重试逻辑没有具体方案 |

## 综合对比

| 维度 | 文档 A（代码描述） | 文档 B（决策规范） | 最终版（融合） |
|------|-------------------|-------------------|---------------|
| **可读性** | ⭐⭐⭐⭐ 简洁 | ⭐⭐⭐ 详细但冗长 | ⭐⭐⭐⭐ 结构化 |
| **准确性** | ⭐⭐⭐⭐⭐ 与代码一致 | ⭐⭐⭐ 理想化 | ⭐⭐⭐⭐⭐ 标注实现状态 |
| **完整性** | ⭐⭐⭐ 缺开拓者/物品 | ⭐⭐⭐⭐ 全覆盖 | ⭐⭐⭐⭐⭐ 全覆盖+状态 |
| **可执行性** | ⭐⭐⭐ 需自行理解 | ⭐⭐ 缺少代码映射 | ⭐⭐⭐⭐⭐ 函数级映射 |
| **维护性** | ⭐⭐⭐⭐ 代码变了改文档 | ⭐⭐ 文档与代码脱节 | ⭐⭐⭐⭐⭐ 状态追踪 |

---

## 最终版做了什么改进

1. **合并两份文档的优势**：文档 A 的代码映射 + 文档 B 的决策全覆盖
2. **每个功能标注实现状态**：✅完成 / 🟡框架就绪 /  部分 / ❌未实现
3. **函数级映射**：每个决策点都标注了对应的函数名（如 `_try_use_upgrade_vouchers()`）
4. **消除冗余**：文档 B 重复了4次的内容压缩为1份
5. **补充缺失**：宝藏召唤框架、上回合重试机制、升级券使用逻辑
6. **增加优先级表**：购买优先级、消耗品使用优先级等表格化呈现
